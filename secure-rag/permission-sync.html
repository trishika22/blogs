Keeping Permissions Fresh: Automatic Permission Sync with Event Grid and Azure Functions

TL;DR. In SecureRAG, every chunk in the search index carries the groups allowed to read it. When a document's permissions changed, the index kept the old ones until the next indexer run, so a user could keep reading a document they had just lost access to. Now, uploading an updated permission file triggers Event Grid, which wakes an Azure Function running inside my private network. The Function works out which documents changed and updates only those chunks. Revocations take effect within seconds, with no re-indexing and no keys stored anywhere.

Part 1: The Problem — Permissions Go Stale

In the original case study, authorization happens at retrieval: each chunk has an access field, and the backend only searches chunks that match the user's Entra groups. That part works. The problem is what happens after a document is indexed.

Same setup as before: Alice is in HR, Bob is in Finance. The company handbook is shared with both.

  • At 10 AM, the company decides Finance shouldn't see the handbook anymore.
  • Someone updates the permissions.
  • But the chunks in the search index still say HR + Finance. Their access values were copied in at indexing time, and nothing updates them until the indexer runs again.

So until then, Bob can keep asking about the handbook and keep getting answers from it. 😬 That gap between what the company decided and what the app enforces is a data leak, and it's what this feature closes.

Part 2: The Design — One Source of Truth, Synced Automatically

The first decision was where permissions live. I made one file the single source of truth: access_control.json, which maps each document to the group names allowed to read it. A second file, groups.json, maps those names to Entra group IDs, because the index stores IDs.

// access_control.json — what the company wants
{
  "company-handbook.md":        ["hr"],
  "employee-leave-policy.md":   ["hr"],
  "employee-benefits.md":       ["hr"],
  "financial-planning-2026.md": ["finance"],
  "budget-guidelines.md":       ["finance"]
}

Nobody edits the search index by hand. The index is a copy the app enforces, and the sync's only job is to keep that copy matching the source. Changes always flow in one direction:

access_control.json → permission sync → access_groups on each chunk
Where permissions liveRoleWho changes it
access_control.jsonSource of truth: what the company wantsPeople (HR, admins)
access_groups on each chunkThe copy the app enforcesOnly the sync
Blob metadata on each documentStarting permissions when a document is first indexedNot yet kept in step (see Part 9)
Design trade-off
Why Event Grid and Azure Functions, and not a simpler option?

I considered two ways to make the sync automatic. GitHub Actions would run the sync whenever access_control.json is pushed: about 45 minutes of work, no networking, and every permission change reviewed in a pull request. Event Grid + an Azure Function reacts to the file being uploaded to Blob Storage, entirely inside Azure, but my storage account is private, so the Function has to join my virtual network.

I chose the harder, Azure-native route, because it's how the same pattern would run in a real deployment where permissions come from storage or SharePoint rather than from a git repo. GitHub Actions stays a good option for "permissions as code."

Part 3: Architecture — What Happens When the File Changes

In words, for the 10 AM scenario:

  • Someone uploads the new access_control.json (handbook → HR only) to the config container.
  • Blob Storage generates a Blob Created event.
  • Event Grid delivers it to the permission_sync Function.
  • The Function finds that only the handbook changed and updates just its chunks.
  • Bob's next search no longer returns the handbook.

Part 4: Event Grid — How Azure Notices the Change

The part that confused me at first: Event Grid doesn't watch or poll anything. Blob Storage itself handles the upload, so it knows the instant a file is written, and as part of finishing the upload it pushes a message to Event Grid. Event Grid is the delivery service that hands that message to whoever subscribed.

It works like a doorbell: it rings when someone presses it, but it doesn't keep a list of who rang yesterday. If you want that history, Blob Storage can keep one too, through resource logs, change feed or versioning, but those are separate features you switch on.

What I created is an event subscription on the storage account. Every subscription has three parts:

PartMy setting
SourceThe storage account holding the config files
FilterEvent type Blob Created, subject begins with /blobServices/default/containers/config/blobs/access_control.json
EndpointAzure Function → permission_sync
Concept
Reading the subject
  • /blobServices/default → the blob service
  • /containers/config → the container
  • /blobs/access_control.json → the file
  • Only events whose subject starts with this path are delivered
Concept
What counts as Blob Created
  • Fires when a blob is created or replaced, so overwriting the file counts
  • Triggered by PutBlob, PutBlockList and CopyBlob
  • Setting blob metadata does not fire an event
Source: Azure Blob Storage as an Event Grid source, Microsoft Learn

A Function isn't the only possible endpoint. The same event could go to a webhook, a Logic App, a Storage queue, Service Bus or Event Hubs, and one storage account can have several subscriptions, each getting its own copy.

Part 5: The Azure Function — Code That Runs Only When Triggered

An Azure Function is a normal Python function that Azure keeps in the cloud and calls for you when its trigger fires. There's no server to manage, it's idle between events, and it scales out on its own. A Function App is the container (settings, identity, networking); a function is one piece of code inside it. Mine runs on the Flex Consumption plan.

The whole entry point is a decorated function:

@app.event_grid_trigger(arg_name="event")
def permission_sync(event: func.EventGridEvent):
    # Only react to access_control.json. Saving sync_state.json into the same
    # container also fires an event, and this check stops it from looping.
    if not event.subject.endswith("/containers/config/blobs/access_control.json"):
        logging.info("Ignoring %s", event.subject)
        return
    logging.info("Permission file changed, syncing.")
    run()

Something I hadn't appreciated: the file runs in two separate moments.

Moment 1
When Azure loads the file
  • Imports run, settings are read, the credential and storage client are created
  • Helper functions are defined, not run
  • The decorator registers permission_sync, which is what makes it appear in the portal
  • The credential doesn't sign in yet; it fetches tokens on first use
Moment 2
Each time an event arrives
  • Azure calls permission_sync directly
  • The subject check runs, then run()
  • If the app is still loaded (warm), Moment 1 is skipped
  • After a quiet period Azure scales to zero, so the next event is a cold start: load first, then run
Design trade-off
Accepting cold starts

Permission changes are rare, so most runs will be cold starts that take a few extra seconds. Flex Consumption can keep "always ready" instances loaded to avoid that, but paying for an always-on instance isn't worth it when a few seconds' delay is still far better than hours.

Part 6: Inside the Sync — Read, Compare, Update, Save

def run():
    new = resolve_policy(read_json("access_control.json", {}), read_json("groups.json", {}))
    old = read_json("sync_state.json", {})
    changes = diff_policies(old, new)

    if not changes:
        logging.info("No permission changes.")
        return

    chunks = chunks_by_document()
    for doc, group_ids in sorted(changes.items()):
        if doc not in chunks:
            logging.warning("%s: no chunks in the index", doc)
            continue
        set_access_groups(chunks[doc], group_ids)
        logging.info("%s: updated %d chunk(s) -> %s", doc, len(chunks[doc]), group_ids)

    write_json("sync_state.json", new)
StepWhat it does
1 · Read what's wantedReads both config files and turns group names into Entra IDs. An unknown group name stops the run instead of being skipped.
2 · Read last timeReads sync_state.json, a snapshot of the permissions last applied to the index
3 · CompareKeeps only the documents whose groups differ; stops early if nothing changed
4 · Find the chunksLooks up which chunk IDs belong to each changed document
5 · UpdateSends a merge for those chunks that changes only access_groups
6 · Save the snapshotWrites the new snapshot, last, so a failure halfway means the next run simply retries

For the 10 AM change, the comparison finds exactly one difference:

DocumentLast timeNowChanged?
company-handbook.mdHR, FinanceHR✅

employee-benefits.mdHRHR—
budget-guidelines.mdFinanceFinance—

Why it's fast: the merge action tells Azure AI Search to change only the access_groups field. The chunk's text and vector are untouched, so nothing is re-chunked or re-embedded, and the very next search uses the new permissions.

Part 7: Reaching Private Storage Without Keys

Two things had to be true for the Function to do its job: it has to reach the storage account, and it has to be allowed in.

Reaching it
VNet integration
  • My storage account is private by company policy; only things inside my VNet can reach it
  • A Function normally runs outside the VNet, just like my laptop
  • VNet integration routes its outgoing traffic through a dedicated subnet in my VNet
  • Inbound public access stays on so Event Grid can deliver events
Being allowed in
Managed identity
  • An identity Azure creates and manages for the Function, like a staff badge
  • The Function asks Azure for short-lived tokens; there's no password to store or leak
  • Roles decide what the badge can do
RoleScopeLets the Function
Storage Blob Data OwnerStorage accountRead the config files and write the snapshot
Search Index Data ContributorSearch serviceRead chunks and update access_groups

For Search to accept those tokens, I switched its API access control to allow both role-based access and API keys, so the existing app keeps working while the Function uses its identity.

Part 9: Known Gaps and What's Next

  • Keep blob metadata in step. Each document's blob metadata still holds its original groups. If the indexer is ever reset, it copies them back and the old permissions return. The fix is for the Function to update the blob's metadata whenever it changes the index, and since setting metadata doesn't fire an event, it won't loop.
  • Look up only the changed documents. The title field isn't filterable, so the sync reads every chunk's ID and title once per run. That's fine at this size; at scale I'd add a filterable document-name field and fetch only the chunks that changed.
  • Proper logging and alerts. Turn on storage resource logs for an audit trail of who changed the permission file, and alert on failed runs.
  • A dedicated storage account for the Function, separate from the documents.

Questions I Asked Myself

Where do permission changes get made: in the JSON file or in the index?

In access_control.json, the single source of truth. The index is a copy that only the sync writes to.

If Blob Storage doesn't keep a log, how does Event Grid know a file changed?

Blob Storage pushes the event at the moment it handles the upload. Event Grid never has to look; it only delivers.

Why compare with a snapshot instead of updating every document each time?

So only real changes touch the index. With five documents it barely matters; with fifty thousand it's the difference between seconds and minutes.

Why save the snapshot last?

If anything fails halfway, the snapshot still shows the old state, so the next run sees the same changes and retries them. Nothing gets silently skipped.
