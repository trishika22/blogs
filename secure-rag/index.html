Engineering Case Study · Access-Controlled RAG
Enforcing Document-Level Access Control in a RAG Pipeline

Part 1: Introduction — What problem was I trying to solve?

Most RAG demos assume that if a document is in the knowledge base, every user can retrieve it. That's not true for many real-world applications.

Imagine an organization with HR and Finance documents. Alice works in HR, while Bob works in Finance. Alice should be able to ask questions about HR policies, but she should never receive information from Finance documents.

I wanted to build a RAG system where document-level authorization is enforced before the retrieved content reaches the LLM.

Part 3: The Core Idea — Authorization Before Generation

How do you stop the LLM from seeing unauthorized documents? 🤔

Enforce authorization before retrieval results reach the LLM. 🔥

One approach is to retrieve everything and tell the LLM not to reveal what the user isn't allowed to see. I didn't rely on that. Once unauthorized content enters the LLM's context, the model has already seen it. A prompt instruction is not an authorization boundary.

Authorization has to happen at the retrieval layer, and it's a separate question from relevance:

  • Authorization: Is Alice allowed to access this document?
  • Relevance: Is this document useful for answering her question?

Alice's identity and group membership determine authorization. Azure AI Search determines relevance.

The LLM is responsible for generating the answer. It is not responsible for deciding what the user is allowed to see.

Part 4: Architecture — What I Built

The system consists of several components working together:

Alice → Microsoft Entra ID → Access Token → FastAPI → Identity + Groups → Azure AI Search → Authorized + Relevant Chunks → Azure OpenAI → RAG Answer

I used two separate Microsoft Entra application registrations — one for the client app Alice interacts with, one for the backend API that handles authentication, authorization, search, and Azure OpenAI.

Document ingestion is a separate pipeline:

Azure Blob Storage → Indexer → Skillset → Document chunks → Azure AI Search

That gives the system two independent sides that meet during retrieval — the document side tags chunks with an access group, the user side resolves a user to their groups. When Alice asks a question, they come together.

Part 5: Document Permissions — Giving Every Chunk an Access Group

Updated October 2026: documents can now belong to several groups, and permission changes sync to the index automatically within seconds. See the changelog.

Every document is assigned an access group during ingestion:

employee-leave-policy.md → HR group
quarterly-finance-report.pdf → Finance group

I use the Entra group ID as the actual access value, not the human-readable name: access = <HR_GROUP_ID>.

That value propagates through ingestion, and has to survive the whole pipeline, because RAG doesn't retrieve documents, it retrieves chunks. Split an HR document into three chunks and all three carry access = <HR_GROUP_ID>.

Azure AI Search stores that value as a filterable field, which gives the backend a common key between a user and a document: Alice maps to HR_GROUP_ID; the HR document maps to HR_GROUP_ID. Same key, both sides.

Part 6: Authentication — How Alice Gets Into the System

Before the backend can decide what Alice can access, it needs to know who she is. I used Microsoft Entra ID for that — the app never touches Alice's password.

Alice → /login → Microsoft Entra ID → Alice signs in → /auth/callback → Access token → FastAPI session

The backend stores the token in the session and validates it on every subsequent request — signature, issuer, audience, scope, claims — rather than trusting whatever's inside it.

Request → Session → Access token → JWT validation → Authenticated user

Once validated, the token gives the backend Alice's identity and group membership directly:

{ "name": "Alice", "groups": ["<HR_GROUP_ID>"], "scope": "access_as_user" }

That's where authentication becomes authorization.

Part 7: Turning Group Membership Into Search Authorization

Alice resolves to a group: Alice → HR_GROUP_ID. The search index resolves the same way — HR chunks carry HR_GROUP_ID, Finance chunks carry FINANCE_GROUP_ID. Same key, both sides.

When Alice asks a question, the backend turns her groups into a search filter: access eq '<HR_GROUP_ID>'.

That filter does two jobs: enforce authorization, and act as a hard constraint on relevance — not a signal. If Alice asks "What is the maternity leave policy?", a Finance chunk might score high on relevance (it mentions "employees," "policy," "benefits"), but it's still excluded — she isn't authorized to see it, regardless of how relevant it is.

Part 8: The RAG Request Flow — and the Security Boundary

This is the part of the architecture I care about most.

Alice authenticates, and her groups resolve to HR_GROUP_ID. When she asks an HR question, the backend queries Azure AI Search with that filter and gets back chunks that are both authorized and relevant — that becomes the grounded prompt sent to Azure OpenAI. When she asks a Finance question instead, the same filter still applies: Finance chunks fail the authorization check and are filtered out before generation — not retrieved and hidden, never retrieved at all.

The security boundary exists outside the LLM. It never sees the document store — only chunks that already passed the authorization check. Unauthorized content is excluded from the retrieval pipeline, not hidden during generation.

Part 9: Grounding the LLM

Authorization solves what information can reach the LLM. Grounding solves a separate problem: what the LLM does when that information isn't enough.

I don't want it filling gaps from general knowledge, so the prompt constrains generation to the retrieved context — answer only from what's provided, don't invent, don't use outside knowledge, and say so when the context is insufficient.

User question + Authorized chunks → Grounded prompt → LLM → Answer

If Alice's authorized documents can't answer her question, the system doesn't bypass the authorization boundary to help — it just says so: "I don't have enough information to answer that."

Two separate protections, two separate jobs: authorization keeps unauthorized information out; grounding keeps the LLM from inventing information when what's authorized isn't enough.

Part 10: Problems I Ran Into

Problem · Storage account blocked all direct uploads

My storage account had public network access disabled by company policy — no direct upload path. I stood up an Ubuntu VM, attached it to a private endpoint on the storage account's VNet, and uploaded documents through that private, network-isolated channel instead of trying to route around the policy.

Problem · Chunks lost their access group

Chunk-level authorization doesn't come for free. When Azure AI Search splits a document into chunks and projects each one as its own searchable entry, only the fields you explicitly map flow down to the child documents — a document-level access field isn't inherited automatically. My first indexer run produced fully chunked, fully vectorized documents with no access value on any of them, so the authorization filter matched nothing. I fixed it by explicitly mapping access into the index projection, so every chunk generated from a document carries its parent's access group forward.

Alice ∈ HR → HR docs ✅ Finance docs ❌
Bob ∈ Finance → Finance docs ✅ HR docs ❌

Part 12: What I Would Improve Next

The core security architecture is in place; the rest is production hardening:

  • Retrieval quality — hybrid keyword + vector search, semantic ranking, and better relevance thresholds.
  • Automated evaluation — Recall@K, Precision@K, and groundedness checks.
  • Infrastructure — replace local client secrets with managed identity, and add observability around auth failures, search queries, and LLM calls.
  • Scaling group membership — for users in many groups, have the LLM narrow the candidate set first: classify the question against a predefined list of groups, then check that prediction against Alice's actual group membership. The LLM only narrows the search; it never grants access — authorization still comes from the intersection with her real, verified groups, never from the prediction alone.

None of it changes the authorization architecture. It's quality and readiness work layered on top of a boundary that's already correct.

This separation is what allows the system to enforce document-level authorization without making the LLM responsible for access control.
